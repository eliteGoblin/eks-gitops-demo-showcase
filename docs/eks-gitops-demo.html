EKS + Terraform + Argo CD + Helm: deployment architecture

Server-side solution for a containerised Go GraphQL API (demo-api) plus an OIDC provider (Keycloak) on AWS EKS, in one region. Prepared 2026-10-16.

In one paragraph: Terraform builds the AWS foundation and installs exactly one thing into Kubernetes: Argo CD. From then on, Git is the source of truth for everything inside the cluster. Argo CD pulls a gitops repo and applies it, using Helm only to render YAML. GitHub Actions tests and builds, pushes the image and chart to ECR, and proposes the new version to the gitops repo as a pull request. CI never holds cluster credentials.

1. Ownership map: what runs where, and who owns it

How to read it:

  • Purple things exist because terraform apply ran. They change only through a Terraform change.
  • Orange things exist because a YAML file is in the gitops repo; Argo CD applies it and keeps re-applying it. Edit the cluster by hand and Argo reverts it.
  • Pink things nobody declares directly: a controller creates them from a Kubernetes object.
    • An Ingress becomes an ALB.
    • An Ingress host becomes a Route 53 record.
    • An ExternalSecret becomes a Secret.
    The pink arrows are those controllers calling AWS APIs, authorised by IAM roles from Terraform through Pod Identity.
  • The EKS control plane (API server, etcd) is run by AWS. Terraform only chooses its settings.
  • Not drawn: the ADOT collector and Fluent Bit (orange, installed by Argo in an observability namespace) that ship traces, metrics and logs to the AWS-managed backends. See App & observability.

3. Bootstrap: from empty account to running app

  1. Bootstrap layer. Run once by hand, with local state that is then migrated into the S3 bucket it just created.
  2. Creates what must outlive any cluster: the state bucket, the ECR repos, the IAM role GitHub Actions assumes through OIDC, and the ACM certificate. Public ACM certificates are free and DNS validation takes minutes, so the certificate survives eks-down/eks-up.
  3. Cluster layer (make eks-up), run from your laptop for the initial build as an IAM admin, never as root. Built 2026-10-16: the IaC pipeline (tf-plan.yaml on pull requests, tf-apply.yaml on main, both via GitHub OIDC roles with trust pinned to the one workflow file) now applies every change under infra/; the argocd root is planned only on main because its plan reads in-cluster Secrets.
  4. Builds the VPC, cluster and nodes. Installs the EKS managed add-ons (vpc-cni and pod-identity-agent before the nodes, so pods get IPs and credentials from the first boot) and the IAM roles for the controllers.
  5. Installs Argo CD and the root Application. Writes the bridge: an Argo CD cluster Secret whose labels say which add-ons to enable and whose annotations carry Terraform outputs (cluster name, VPC id, region, domain). From here on Terraform stops.
  6. Argo CD syncs bootstrap/ in the gitops repo and creates the addons and apps Applications (app of apps).
  7. Sync waves order things: add-ons first (wave 0), then Keycloak and demo-api (wave 1).
  8. Controllers turn Kubernetes objects into AWS resources: an ALB with the ACM certificate, DNS records, Secrets. The app is reachable at https://app.frankbluemind.com.

Teardown (make eks-down): delete the Ingresses first so the LB controller removes the ALB, then run terraform destroy on infra/eks. Otherwise an orphaned ALB blocks VPC deletion. The bootstrap layer stays.

Note: why Terraform stops at Argo CD. Installing every add-on with Terraform's Helm provider looks simpler but ages badly:

  • The provider needs a running cluster at plan time, which doesn't exist on the first create.
  • Drift stays invisible until the next apply.
  • Chart values and release state end up in Terraform state, and every plan gets slower.

Argo CD reconciles continuously, shows a diff before each change, and uses the same rollback and audit model as the app. Rule: an AWS API object goes in Terraform; a Kubernetes object goes in Git + Argo CD. The EKS managed add-ons follow the rule: they are configured through the AWS EKS API, so Terraform manages them.

  • App of apps: the root Application's manifests are themselves Applications. After bootstrap, adding a component means adding a file. No Terraform, no kubectl.
  • ApplicationSet + cluster generator: each add-on file is a template. It produces an Application for every cluster Secret carrying the matching enable_* label and fills in values from that Secret's annotations. That is how Terraform outputs reach Helm values without hard-coding.
  • Sync policy: dev uses automated with prune (delete what was removed from Git) and selfHeal (undo manual edits). Prod is the same, but its files change only through approved pull requests.
  • Waves gotcha: Argo does not wait for a child Application to become healthy before starting the next wave unless the Application health check is turned back on in argocd-cm. Add it so apps start after the add-ons are healthy.

5. Helm: render engine, ECR as the chart repo

Note: yes, Helm is only the render engine. The repo-server runs helm template chart --values …, and the application-controller diffs that YAML against the live cluster and applies it. Argo never runs helm install. The consequences:

  • There are no Helm release records, so helm list is empty and helm rollback does nothing. Rollback = revert the commit in the gitops repo.
  • Helm hooks are mapped to Argo phases, e.g. pre-upgrade → PreSync and post-install → PostSync.
  • Helm's lookup returns nothing, so charts must not depend on it.
  • Argo labels what it applied and can prune leftovers, which a plain helm template | kubectl apply cannot.

The chart is a versioned artifact, like the image.

  • CI packages deploy/helm/demo-api once per merge (0.1.N) and pushes it to ECR as an OCI artifact, next to the image. No separate chart server is needed.
  • An environment is chart version + values file, so prod runs the exact bytes that were tested in dev.
  • Gotcha: ECR tokens expire every 12 hours. Argo's repository credential is refreshed by an external-secrets ECRAuthorizationToken generator, which uses Pod Identity too.

6. Release flow: commit to running pod

② PR checks
go vet, go test -race, golangci-lint, govulncheck, codegen drift check (gqlgen generate + git diff --exit-code), helm lint + kubeconform on the rendered chart, image build + Trivy scan. Nothing is pushed.
④–⑤ Build
arm64 image tagged with the git SHA, plus an SBOM and a cosign keyless signature. Chart packaged as 0.1.<run>. Both are pushed to ECR with short-lived credentials from GitHub OIDC; the role may only push to these repos.
⑥ Promote
A bot opens a PR in the gitops repo changing two lines: targetRevision in apps/dev/demo-api.yaml and image.tag in values/dev/demo-api.yaml. Dev auto-merges. This demo builds dev only; prod would be the same change in the prod files with a required approval (explained, not shown).
⑦–⑧ Deploy
Argo CD notices the commit (polling, or a webhook for speed), renders, diffs and applies. Kubernetes rolls the pods; readiness probes keep traffic on the old pods until the new ones answer. A PostSync Job runs the end-to-end smoke checks.
Rollback
Revert the promotion commit; Argo syncs back to the previous chart and tag.

Note: CI never talks to the cluster. It writes only to ECR and Git. No kubeconfig and no long-lived AWS keys are stored in GitHub. If CI is compromised, the attacker can propose a change but cannot apply it, and every change leaves a commit.

7. Runtime: a request, a login, a secret

  • Ingress: one ALB, shared through group.name, serves both hosts. TLS ends at the ALB with the ACM certificate. target-type: ip sends traffic straight to pod IPs; the VPC CNI gives pods real VPC addresses.
  • Argo CD UI: public at argocd.frankbluemind.com on the same ALB, login only through Keycloak SSO (OIDC client argocd in realm demo; Keycloak groups map to Argo RBAC roles). The local admin account is disabled after bootstrap.
  • Grafana: public at grafana.frankbluemind.com on the same ALB, Keycloak SSO; the shared demo.guest login is Viewer. Who can do what: Identity and access.
  • OIDC issuer rule: the issuer is https://auth.frankbluemind.com/realms/demo, the same string for the browser and the API pod. The API fetches discovery and JWKS from that public host and caches them. Keycloak runs with KC_HOSTNAME set and trusts the ALB's forwarded headers.
  • Secrets: Secrets Manager → ESO → Kubernetes Secret; Git holds only the reference. Details in Secrets.
  • Hardening:
    • Pods run non-root with a read-only root filesystem and all capabilities dropped.
    • Every response carries a Content-Security-Policy (default-src 'none' for the API; the pages list exactly what they load), Cross-Origin-Opener-Policy and a minimal Permissions-Policy.
    • The namespace enforces the Pod Security Standard restricted.
    • NetworkPolicies (enforced by the VPC CNI) allow ALB → pods and API → Keycloak only.
    • The API endpoint is limited to your IP.
  • Production differences:
    • Nodes in private subnets, with NAT or VPC endpoints.
    • Keycloak via its Operator with Postgres on RDS, or a managed IdP (Cognito, Entra ID). Swapping is a configuration change for the API.
    • Two or more replicas plus a PodDisruptionBudget.

8. Secrets: store, delivery, rotation

KISS model: AWS Secrets Manager holds the only real copy. Git holds pointers (ExternalSecret objects), never values. The External Secrets Operator (ESO), a CNCF project installed by Argo, copies each value into a Kubernetes Secret and keeps it refreshed. The app reads normal env vars or files and never knows AWS is involved. In an enterprise, swap Secrets Manager for HashiCorp Vault: pods authenticate with Vault's Kubernetes auth method, and ESO or the Vault Secrets Operator delivers.

A secrets-only merge never redeploys (release.yaml ignores secrets/**). Runbook: scripts/rotate-secret-demo.sh (README, which also gives the measured timings).

9. State and scaling

Why: to scale, the API must hold no state in the pod. Today it keeps data in memory with 1 replica, so 2 pods would show different data. Auth is already stateless: JWTs are validated locally against cached JWKS, and the SPA holds the session. Moving data to a shared database makes every pod interchangeable.

DecisionOptionsChoice and why
State
  • chosen RDS Postgres db.t4g.micro, single-AZ, private subnets (~US$0.02/h)
  • Postgres pod in the cluster: free, but data dies with the pod; weaker story
  • DynamoDB: serverless, but the domain is relational
  • Aurora Serverless v2: scales to zero, but cold starts and higher cost
Managed and realistic for ~50¢/day. Terraform infra/eks/rds.tf creates it and destroys it with the cluster. manage_master_user_password = true: RDS generates and rotates the password in Secrets Manager, ESO delivers it, so it shows the full secrets flow with no custom rotation code. Migrations + seed run as an Argo PreSync Job. App change: a Postgres store (sqlc + pgx) replaces the in-memory store; local dev gets a Postgres container in docker-compose.
Autoscaling
  • chosen HPA (autoscaling/v2) on CPU
  • KEDA: scales on events or Prometheus queries (requests/s, p95, queue depth), down to zero; manages an HPA for you
  • VPA: right-sizes requests; don't combine with HPA on the same CPU metric
  • Karpenter / Cluster Autoscaler: adds nodes when pods don't fit; complements HPA
Built in, needs only metrics-server (already an add-on). Min 2, max 6, 60% CPU, scale-down window 120 s for the demo. Gotchas: CPU % is relative to requests (chart sets 50m); readiness probes + a PodDisruptionBudget keep scaling safe; remove replicas from Git or set Argo ignoreDifferences on /spec/replicas, or Argo fights the HPA. Upgrade path: KEDA on requests/s or p95 once Prometheus exists (GraphQL query cost varies, so CPU is only a proxy); Karpenter if pods outgrow 2 nodes.

Scaling demo:

  1. Generate load with hey or k6 against https://app.frankbluemind.com/graphql using a real token.
  2. Watch kubectl get hpa,pods -w: replicas go 2 → 6; the ALB registers new pod IPs automatically (target-type: ip).
  3. Run the same query repeatedly: identical results from every pod, proving shared state.
  4. Stop the load: after the cool-down it scales back to 2.

Connection sizing: 6 pods × pool of 10 = 60 connections, under t4g.micro's ~80 max_connections. Beyond that, add RDS Proxy. 6 small pods fit easily on 2 × t4g.large, so node scaling isn't needed for the demo.

11. Decisions

DecisionContextOptionsChoice and whyRevisit when
IngressSomething must route HTTPS traffic to demo-api and Keycloak.

Naming: "ALB Ingress Controller" is the old name (v1, kubernetes-sigs/aws-alb-ingress-controller). Since its renaming around 2020 it is the AWS Load Balancer Controller (v2+), which also provisions NLBs for Service type LoadBalancer.
  • chosen ALB via the AWS Load Balancer Controller (Ingress)
  • Gateway API with an in-cluster Envoy gateway (kgateway, Envoy Gateway, Istio) behind an NLB
  • ALB in front of an in-cluster gateway
 Is ALB current best practice? It is the most common AWS-native default: AWS runs the data plane, ACM and WAF are built in, and it is the least to operate. For routing APIs, the industry is moving to Gateway API: ingress-nginx is retired, and kgateway (formerly Gloo, a CNCF project built on Envoy) adds API-gateway features such as rate limits, JWT validation and weighted canaries. A common enterprise pattern puts an NLB or ALB in front of an in-cluster Gateway API gateway. The LB controller also supports Gateway API now (HTTPRoute → ALB); it is recent, so verify maturity first.
For this demo: ALB. No proxy pods, so it fits on 2 nodes.		 We need rate limiting, JWT validation at the edge, weighted canaries, or portability across clouds.
HTTPSThe PKCE login needs a secure context (crypto.subtle), and Keycloak's default sslRequired=external refuses plain HTTP. No CA issues certificates for *.elb.amazonaws.com.
  • chosen Real domain + ACM certificate on the ALB
  • CloudFront default *.cloudfront.net: no domain, but needs a Terraform-owned ALB + TargetGroupBinding, and the URL changes on every rebuild
  • Self-signed certificate on the ALB: browser warning, and the API pod must trust the CA
  • Plain HTTP: breaks PKCE and Keycloak login
 Domain eksgitops.click at US$3/year: the fewest moving parts, stable hostnames, a free ACM certificate (bootstrap layer, auto-renews), and the same shape as production. kubectl port-forward remains the zero-cost local option.

Where TLS ends: at the ALB; ACM certificates cannot be mounted into pods. ALB → pod is HTTP inside the VPC. For end-to-end TLS in production, use HTTPS to the pods or a service mesh. If TLS ended in-cluster instead (e.g. a Gateway API gateway such as kgateway), use cert-manager + Let's Encrypt, with DNS-01 validation for the wildcard.

 The domain lapses, or a no-domain throwaway environment is needed (use CloudFront then).
