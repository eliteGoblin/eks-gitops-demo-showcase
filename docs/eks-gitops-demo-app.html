App, identity and observability

Companion to the platform page and the code architecture page: what the app does, who can log in to what, which GraphQL features it shows, how it is observed with OpenTelemetry, and the build order. Prepared 2026-10-16. Phase 1 is built (the API, service kit, playground, CI and bootstrap infrastructure); later phases are design.

Decisions recorded 2026-10-16

  • End state: a public demo of three things: the app (login + GraphQL calls), Argo CD, and the OpenTelemetry dashboards.
  • Repo: the app lives in eks-gitops-demo, structured as clean architecture on a shared service kit.
  • Environments: dev only. Promotion to prod is explained, not shown.
  • Request flow: a participant raises a support request against their plan; agency staff approve or reject it; approval reserves budget as a service booking; the provider later claims against the booking. Nobody may decide their own request.
  • Public hosts on one ALB and the wildcard certificate, all signing in through Keycloak at auth.frankbluemind.com: app., argocd. and grafana.frankbluemind.com. The Keycloak admin console is not routed publicly.
  • Identities: zhaolin.sun (admin of Argo CD and Grafana, and a participant who raises requests), case.officer (staff approver), demo.guest (shared read-only login for reviewers).
  • Passwords: random per user but memorable (word-word-number-symbol), kept in Secrets Manager and put into the realm at import time; never in Git (see Identity).
  • Keycloak runs in production mode with its own database on RDS, so users persist; RDS therefore moves to phase 2.
  • Dashboards: self-hosted Grafana as the UI over AWS-managed backends (X-Ray, Managed Prometheus, CloudWatch Logs).
  • Terraform: applied from the laptop for the initial build; the IaC pipeline (plan on PR, apply on merge via GitHub OIDC) was added on 2026-10-16 and owns changes under infra/ from then on.
  • Prerequisites: an IAM Identity Center admin for running Terraform (not root), and the domain's contact-email verification.

1. App domain: a support-funding service

A participant receives a plan with a budget per support category. The participant (or a nominee acting for them) raises a support request: category, description, estimated amount and optionally a preferred provider. Agency staff approve or reject it with a reason; approval reserves part of the budget as a service booking for a provider. The provider delivers the service and claims payment against the booking. The plan's management type decides who may claim. A claim is a payment request against a budget, not an insurance claim.

Grey = people and organisations (also the callers); blue = records. Approving a support request creates the service booking. Every read and write passes the relationship checks in the use cases: nominee delegation, provider booking, plan management type, and separation of duties.

SDL sketch of the new types (the design; the built schema is internal/adapter/graphql/schema/schema.graphqls) 
interface Node { id: ID! }
interface Party { id: ID!  displayName: String! }
interface UserError { message: String!  path: [String!] }

enum PlanManagement { AGENCY PLAN_MANAGED SELF }
enum SupportCategory { DAILY_LIVING THERAPY EQUIPMENT }
enum SupportRequestStatus { SUBMITTED APPROVED REJECTED }
enum OrderDirection { ASC DESC }
enum ClaimOrderField { SUBMITTED_AT AMOUNT }

type Participant implements Node & Party {
  id: ID!
  displayName: String!
  memberNumber: String!
  schemeNumber: String! @deprecated(reason: "Use memberNumber; removal after 2026-12-31")
  dateOfBirth: Date            # null unless the caller may see it
  plans: [Plan!]!
}
type Provider implements Node & Party { id: ID!  displayName: String!  bookings: [ServiceBooking!]! }
type ServiceBooking implements Node {
  id: ID!  plan: Plan!  provider: Provider!  category: SupportCategory!  reserved: Money!  remaining: Money!
}
type SupportRequest implements Node {
  id: ID!  plan: Plan!  category: SupportCategory!  description: String!
  estimatedAmount: Money!  preferredProvider: Provider
  status: SupportRequestStatus!  decisionReason: String
  booking: ServiceBooking      # set when approved
}

union SearchResult = Participant | Provider | Claim

input ClaimFilter {           # submittedAfter is inclusive, submittedBefore exclusive (RFC 3339)
  status: ClaimStatus  category: SupportCategory  providerId: ID  submittedAfter: String  submittedBefore: String
}
input ClaimOrder { field: ClaimOrderField! = SUBMITTED_AT  direction: OrderDirection! = ASC }
input SubmitSupportRequestInput {
  planId: ID!  category: SupportCategory!  description: String!  estimatedAmount: Money!  preferredProviderId: ID
}
input DecideSupportRequestInput { id: ID!  approve: Boolean!  reason: String!  providerId: ID }
input SubmitClaimInput {
  bookingId: ID!  amount: Money!  serviceDate: Date!
  idempotencyKey: String       # optional; same key + same input → the same Claim, never a second payment
}

type ValidationError implements UserError { field: String!  message: String!  path: [String!] }
type BudgetExceededError implements UserError { message: String!  path: [String!]  remaining: Money!  requested: Money! }
type SelfApprovalNotAllowedError implements UserError { message: String!  path: [String!] }
type IdempotencyKeyReusedError implements UserError { message: String!  path: [String!] }

union SubmitSupportRequestPayload = SupportRequest | ValidationError | BudgetExceededError
union DecideSupportRequestPayload = SupportRequest | SelfApprovalNotAllowedError | ValidationError
union SubmitClaimPayload = Claim | ValidationError | BudgetExceededError | IdempotencyKeyReusedError

type Query {
  node(id: ID!): Node
  nodes(ids: [ID!]!): [Node]!
  search(term: String!, first: Int = 10): [SearchResult!]!
  claims(filter: ClaimFilter, orderBy: ClaimOrder, first: Int = 20, after: String): ClaimConnection!
}
type Mutation {
  submitSupportRequest(input: SubmitSupportRequestInput!): SubmitSupportRequestPayload! @auth(requires: [PARTICIPANT, NOMINEE])
  decideSupportRequest(input: DecideSupportRequestInput!): DecideSupportRequestPayload! @auth(requires: [AGENCY_STAFF])
  submitClaim(input: SubmitClaimInput!): SubmitClaimPayload! @auth(requires: [PROVIDER])
}
type Subscription {
  supportRequestStatusChanged(planId: ID!): SupportRequest!
  claimStatusChanged(planId: ID!): Claim!
}

Plan, Claim and the connection types also implement Node; existing types are unchanged apart from the renames. The self-approval check is a domain rule (see the code page); the @auth directive only gates the role.

Passwords. The five demo users get random passwords that stay memorable (word-word-number-symbol, from a CSPRNG). make secrets-seed writes them to Secrets Manager (demo/keycloak/users); an ExternalSecret hands them to the realm Job as environment variables and keycloak-config-cli substitutes them at import time, re-setting them on every import. Git and the realm ConfigMap hold only $(env:PW_<USERNAME>) placeholders, so Argo CD's read-only role, which can read ConfigMaps, learns nothing. The generated client secrets above take the same path and are never human-typed.

Accepted risk: a public site with shared demo logins. Cheap mitigations: Keycloak brute-force detection; guests are read-only in Argo CD and Grafana; only zhaolin.sun is an admin; the Keycloak admin console is not routed; optionally an ALB IP allowlist on argocd.frankbluemind.com; rotate the passwords after use (ROTATE_DEMO_PASSWORDS=1 make secrets-seed, then sync the realm).

Production path: no shared logins, and TOTP MFA required for admin groups.

4. Observability: OpenTelemetry metrics and traces

Decision: the app speaks only OpenTelemetry (OTLP). An in-cluster ADOT collector (AWS Distro for OpenTelemetry) forwards traces to AWS X-Ray and metrics to Amazon Managed Service for Prometheus; logs go to CloudWatch Logs through Fluent Bit. Self-hosted Grafana (one small pod, installed by Argo) is the UI over all three, with Keycloak SSO. The collector is the single seam for data, Grafana the single seam for viewing: changing a backend is config, never app code.

Grafana runs in the same cluster; it is drawn on the right because it only reads from the backends.

What we measure and alert on

  • RED per GraphQL operation (built): request rate, errors by extensions.code, latency histogram (p50/p95/p99).
  • What counts as an error: outcome="error" only when the server failed (INTERNAL, UNAVAILABLE, or an unknown code). The caller's mistakes and denials (BAD_USER_INPUT, FORBIDDEN, UNAUTHENTICATED, parse/validation/depth/complexity rejections, RATE_LIMITED) are outcome="client_error"; business results returned as union members (e.g. BudgetExceededError) are data, outcome="ok". The error-rate alert counts server errors only, so a user typing a bad amount cannot page anyone.
  • Security signals: 401/403 counts, 429 rate-limit rejections, complexity and depth rejections.
  • Dependencies: DB pool in-use/idle/max (built); payments-svc calls as client spans in the approval's trace (built); circuit-breaker state changes as warning logs (a breaker metric is not built).
  • Business counters (planned): support requests raised, approved, rejected; claims submitted, approved; budget-exceeded outcomes.
  • Runtime: Go heap, goroutines, GC pauses.
  • Sampling: 100% in the demo; parent-based 10% in production.
  • Alerts (Grafana alerting → SNS email): server error rate > 5% for 5 min (built); p95 > 500 ms and a spike in 401s (planned).
  • One dashboard: RED per operation, HPA replica count, DB connections. The scaling load test is visible on it, and KEDA can later scale on the same AMP query (requests/s).

5. Public-demo guardrails

  • Least privilege for guests everywhere: demo.guest is a participant in the app, role:readonly in Argo CD (cannot sync, delete or see secrets), and Viewer in Grafana.
  • Admin only for zhaolin.sun in Argo CD and Grafana; the Keycloak admin console is not routed publicly.
  • Keycloak brute-force detection locks an account after repeated failures.
  • API protection: the rate-limit middleware (token bucket per IP and subject) plus GraphQL depth and complexity limits.
  • Cost: the budget alert (~US$60/month) and make eks-down between sessions.
  • Optional: AWS WAF managed rule groups on the ALB (about US$5/month per web ACL plus per rule group), and an IP allowlist for argocd.frankbluemind.com.
  • After use: rotate every demo password and client secret.
